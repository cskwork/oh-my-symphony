# Safe Windows managed-service stop design

## Problem

Windows managed services are launched with `CREATE_NEW_PROCESS_GROUP` and
`DETACHED_PROCESS`. Plain `symphony service stop` calls non-forced
`taskkill /T`, waits, and then returns failure unless the operator also passed
`--force`. In a normal unsandboxed host test, the real backend process-tree
regression passes and explicit `service stop --force` succeeds, but plain
service stop leaves the detached orchestrator alive.

Sandboxed `taskkill` can additionally return access denied. That is an
environment boundary: the exact process-tree test passes outside the sandbox.
This change must not add a second PID-enumeration kill implementation merely to
bypass the sandbox.

## Decision

After the existing bounded non-forced Windows stop attempt, allow plain service
stop to use the existing forced tree-kill primitive only when the live HTTP
identity probe proves that the recorded host/port serves both the exact recorded
workflow and the exact random service-instance ID created for that launch. Run
this probe even when the launcher exits or was already absent, because its child
may survive. The same response must report the positive PID of the process
serving the API; that proved PID, not the launcher's recorded PID, is the
forced-kill target.

This distinction is required by the real Windows data shape. The venv launcher
PID saved in the service record remains alive as the parent of a second Python
process that serves the API, so launcher PID and `os.getpid()` are intentionally
different. A per-launch ID survives wrappers and re-exec without assuming one
fixed parent depth. `orchestrator_pid` remains additive health observability;
`service_instance_id` is also a health-only lifecycle capability, generated by
managed start from 256 random bits. It is stored in the private service record
and must not be logged or exposed as a general operator credential. Health
authentication additionally requires a URL-safe 32–128 character shape; short
or malformed legacy correlation IDs never authorize the header path.

The sequence is:

1. Load the service record.
2. If its recorded launcher PID appears live, attempt the existing non-forced
   tree termination and wait for the configured timeout.
3. On Windows only, when `--force` was not supplied and the record carries a
   non-empty service-instance ID, probe the recorded API for exact workflow and
   instance identity regardless of launcher liveness. The serving child may
   survive after its launcher exits or may already be orphaned at entry.
4. Strictly validate the positive integer `orchestrator_pid` from that same
   response. Recheck that proved PID immediately before invoking the existing
   forced tree termination against it.
5. Wait for both the proved orchestrator PID and recorded launcher PID to exit.
   If either remains, fail closed and retain the record.
6. If identity proof is unavailable, mismatched, or malformed, perform no
   automatic force and retain the record even if the launcher PID is absent;
   a token-bearing child may still survive without its launcher.
7. Continue to reserve active-backend registry sweeping for explicit
   `--force`.

## Safety properties

- No new process-enumeration or Win32 termination implementation.
- No automatic elevation.
- No automatic forced escalation against the reusable recorded launcher PID.
  Automatic force targets only the PID returned by the exact workflow and
  exact per-launch instance response.
- POSIX behavior remains byte-for-byte unchanged.
- Legacy records without an instance ID and unreachable or mismatched records
  remain fail-closed and are retained while their recorded launcher is live.
- The public CLI shape remains unchanged. The private service-record schema
  gains one optional backward-compatible field; health gains additive nullable
  `service_instance_id` and positive `orchestrator_pid` fields.
- The instance ID is generated with `secrets.token_urlsafe(32)`, overwrites any
  inherited value only in the copied child environment, is consumed into
  orchestrator state, and is removed before hooks/backends can inherit it.
- Instance IDs are bounded to 128 characters and normalized through one shared
  protocol helper.
- Plain Windows stop now means bounded non-forced attempt followed by an
  owned-root forced escalation; explicit `--force` additionally authorizes
  registry/workspace backend sweeping.

## Rejected approaches

- Toolhelp/ctypes descendant fallback: unnecessary on a normal host and adds
  PID-reuse/race blast radius.
- Blind forced escalation: could kill an unrelated process after PID reuse.
- Forcing the recorded launcher after a token match: the launcher can exit and
  its PID can be reused while the proved child survives.
- Matching `health.parent_pid` to the recorded launcher: brittle with deeper
  wrappers and still based on a reusable PID.
- Treating wrapper exit as tree cleanup: descendants may survive.
- Cooperative shutdown endpoint: safer long-term graceful control but a much
  wider API/security decision than this defect requires.

## Verification

- New red test proves plain Windows stop escalates only for an exact workflow
  and instance ID, and targets the health-reported PID even when it differs
  from the recorded launcher.
- Characterization test proves an unreachable/mismatched API never escalates.
- A reused recorded launcher PID is never the automatic forced-kill target.
- Record round-trip, legacy record, spawn-environment override, health direct/
  HTTP, malformed token/PID, and token non-propagation tests cover the contract
  end to end.
- Existing force-stop and POSIX tests remain green.
- Real unsandboxed service start/normal-stop closes the port and clears record.
- Unreachable, mismatched, or malformed proof with an absent launcher retains
  the record and never forces a PID.
- Full static, unit, integration, browser, live pipeline, and QA evidence gates
  must pass before commit/push.
