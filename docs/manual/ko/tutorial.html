  1. Symphony가 무엇인가

    Symphony는 내 컴퓨터에서 도는 오케스트레이터(orchestrator, 여러 에이전트를 지휘하는 프로그램)다. 칸반 보드를 poll(주기적 조회)하고, 티켓마다 내가 고른 AI 코딩 에이전트를 붙이고, 그 에이전트들을 각자 격리된 git worktree(작업 트리, 같은 저장소의 별도 체크아웃) 안에서 동시에 돌린다. 진행 상황(턴 수, 토큰, 마지막 이벤트)은 터미널 칸반인 TUI(터미널 화면)나 http://127.0.0.1:9999/의 내장 웹 보드에서 본다. 티켓은 코드 옆에 놓인 Markdown 파일이라 SaaS도, API 키도, 가입도 없이 써볼 수 있다.

    install→project create / add→doctor→tui / service→ticket→agent runs→Human Review→Done

    자는 동안 무인 리팩터링을 돌리는 1인 개발자, 버그 수정을 여러 에이전트에 병렬로 나누는 팀, 여덟 에이전트를 같은 작업으로 비교하는 연구자, 그리고 "에이전트당 채팅 창 하나"의 한계에 부딪힌 누구에게나 맞는다.

  3. 설치

    목표: symphony 명령이 들어 있는 가상환경.

    git clone https://github.com/cskwork/oh-my-symphony.git
cd oh-my-symphony
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
symphony --version

    확인: symphony 0.22.0이 출력된다.

  4. 프로젝트 만들기 또는 등록하기

    목표: 내 프로젝트 디렉터리. oh-my-symphony 체크아웃은 컨트롤 플레인(control plane, 지휘소)으로 남긴다. doctor와 일반 실행은 Symphony 자체 저장소 안의 WORKFLOW.md를 거부하므로, 에이전트가 자신을 띄운 오케스트레이터를 고칠 수 없다.

    symphony project create "My App" --path ../my-app
# or adopt an existing directory; Git and missing Symphony files are added safely
symphony project add /path/to/existing-project --name "My App"
cd ../my-app

    확인: 없는 경로는 새 Git 저장소가 된다. Git이 아닌 기존 디렉터리는 그 자리에서 초기화된다. 기존 Git 저장소는 메타데이터와 파일을 그대로 유지한다. Symphony는 빠진 운영 파일만 추가하고 관련 없는 변경은 절대 스테이징하지 않는다.

    Git이 아니던 디렉터리라면: Symphony는 자신이 추가한 파일만 커밋한다. 기존 제품 파일은 추적되지 않은 채 남으므로, 티켓을 보내기 전에 직접 검토하고 커밋해야 워커의 worktree에 포함된다.

  5. 생성된 WORKFLOW.md 읽기

    목표: 첫 실행에 중요한 네 블록을 이해한다. 프로젝트의 WORKFLOW.md를 연다(기본 제공 파일 트래커 템플릿은 WORKFLOW.file.example.md).

    tracker:
  kind: file
  board_root: ./kanban
  active_states: [Todo, "In Progress", Verify, Document]
  terminal_states: ["Human Review", Done, Blocked, Archive]

workspace:
  root: ~/symphony_workspaces

hooks:
  # Each ticket gets its own workspace at workspace.root/<ID>, attached as a
  # git worktree of the host repo on a symphony/<ID> branch.
  after_create: |
    bash "$SYMPHONY_WORKFLOW_DIR/scripts/symphony-setup-worktree.sh"

agent:
  kind: codex          # codex | claude | gemini | agy | kiro | opencode | pi | prime-agent
  max_concurrent_agents: 1

server:
  port: 9999

prompts:
  base: ./docs/symphony-prompts/file/base.md
  stages:
    Todo: ./docs/symphony-prompts/file/stages/todo.md
    "In Progress": ./docs/symphony-prompts/file/stages/in-progress.md
    Verify: ./docs/symphony-prompts/file/stages/verify.md
    Document: ./docs/symphony-prompts/file/stages/document.md
    Done: ./docs/symphony-prompts/file/stages/done.md

    tracker(트래커, 티켓 저장소)는 티켓이 어디 있고 어떤 컬럼이 있는지 정한다. hooks는 에이전트 턴 앞뒤로 실행되는 스크립트다. 기본값은 워크스페이스를 worktree로 붙여서 호스트 작업 트리를 건드리지 않는다. agent.kind가 에이전트를 고른다. 주석에 있는 값 중 claude, pi 등으로 바꾸면 이름이 같은 블록(claude:, pi:, …)만 실행에 쓰인다. prompts는 base와 티켓의 현재 상태에 해당하는 파일 하나만 보낸다.

    확인: WORKFLOW.md 옆에 kanban/ 디렉터리가 있고, agent.kind가 설치한 CLI와 일치한다.

  6. symphony doctor로 preflight(사전 점검)

    목표: 무엇이든 띄우기 전에 흔한 첫 실행 실패를 잡는다.

    symphony doctor ./WORKFLOW.md

    확인: 점검 항목당 한 줄.

    PASS  server.port=9999              127.0.0.1:9999 is free
PASS  agent.kind=claude             claude → /usr/local/bin/claude
FAIL  hooks.after_create            contains placeholder 'my-org/my-repo' — every dispatch will fail with rc=128. Switch to the worktree default or replace with a real clone / `: noop`.
PASS  workspace.root=~/symphony_workspaces  exists and is writable
PASS  tracker.board_root            ./kanban (3 tickets)

    종료 코드 0은 전부 통과, 1은 FAIL이 하나 이상, 2는 WORKFLOW.md 자체를 읽지 못했다는 뜻이다. doctor는 포트 충돌, $PATH의 CLI 누락, 자리표시자 클론 URL, 쓰기 불가 워크스페이스, 보드 디렉터리 누락을 잡는다. FAIL 줄이 가리키는 것을 고치고 깨끗해질 때까지 다시 돌린다.

  7. 선택: 에이전트 없이 먼저 돌려보기

    목표: 내장 mock(가짜) 백엔드로 카드가 살아 움직이는 것을 본다. 이 단계는 선택이다. 실제 CLI가 준비됐다면 건너뛴다. mock은 Codex와 같은 프로토콜을 쓰지만 턴과 토큰 증가를 흉내 낼 뿐 실제 작업은 하지 않는다.

    symphony project create "Symphony Demo" --path ../symphony-demo
cd ../symphony-demo

cat > WORKFLOW.md <<'YAML'
---
tracker: { kind: file, board_root: ./kanban,
           active_states: [Todo, "In Progress", Verify, Document],
           terminal_states: ["Human Review", Done, Blocked, Archive] }
polling: { interval_ms: 5000 }
workspace: { root: ~/symphony_workspaces }
hooks:
  after_create: ": noop"
  before_run:   ": noop"
  after_run:    "echo done"
agent:  { kind: codex, max_concurrent_agents: 1, max_turns: 4, max_total_turns: 60 }
codex:  { command: python -m symphony.mock_codex }
server: { port: 9999 }
---
You are picking up ticket {{ issue.identifier }}: {{ issue.title }}.
YAML

symphony board init ./kanban
symphony board new TASK-1 "smoke test"
symphony tui ./WORKFLOW.md

    확인: 약 5초 안에 Todo 컬럼의 TASK-1에 초록색 ●가 생기고 턴 카운터와 토큰 합계가 올라간다. Ctrl-C로 종료한다.

    mock에서는 카드가 Todo에 머문다. 실제 에이전트만 kanban/TASK-1.md를 다시 써서 카드를 옮긴다. mock은 오케스트레이터 → 백엔드 → 워크스페이스 → hooks 파이프라인이 LLM 호출 없이 끝까지 도는지 증명하는 용도다.

  8. 티켓 추가하기, 세 가지 방법

    목표: kanban/TASK-1.md 파일 하나. 실제 프로젝트로 돌아와서:

    symphony board new TASK-1 "Fix flaky pagination test" \
  --priority 2 \
  --labels backend,test \
  --description "tests/test_pagination.py::test_cursor_advance is flaky on CI."
# → created kanban/TASK-1.md

symphony board ls                    # all tickets
symphony board show TASK-1           # full body

    두 번째 방법은 TUI다. 보드에서 n을 누르면 여러 줄 본문을 가진 새 티켓을 등록한다(파일 보드 전용). e는 포커스된 티켓을 편집한다. 세 번째는 웹 보드다. Board 페이지에서 CLI와 같은 검증을 거쳐 이슈를 만들고 고치고 지운다.

    확인: board new는 쓰기 전에 검증한다. id는 ^[A-Za-z][A-Za-z0-9_-]{0,63}$에 맞아야 하고, 상태는 tracker.active_states / terminal_states 안에 있어야 하며, 모든 --blocked-by 대상이 보드에 존재해야 한다. --agent-kind codex를 붙이면 이 티켓만 다른 에이전트로 고정한다.

  9. TUI를 띄우고 보드 읽기

    목표: 내 티켓이 디스패치(dispatch, 워커 투입)되는 것을 본다.

    symphony tui ./WORKFLOW.md

    확인: 컬럼은 트래커 상태다(active_states가 먼저, 그다음 terminal_states). 한 번의 폴 틱(polling.interval_ms, 기본 30초) 안에 오케스트레이터가 워커를 보내고, 카드에 초록색 ●와 턴 카운터, 토큰 합계가 나타난다. 노란 ↻는 재시도 큐에 있다는 뜻이고, ✓는 이번 세션에서 완료됐다는 뜻이다.

    키지금 눌러보기
    ?모든 키를 묶어 보여주는 도움말 모달 (esc로 닫기)
    tab / enter다음 카드로 포커스 / 그 카드의 상세 모달 열기
    p상세 패널 표시·숨기기. ]로 패널에 포커스, [로 복귀
    P포커스된 실행 중 워커 일시정지 / 재개
    /id · 제목 · 라벨로 카드 필터. esc로 해제
    ●는 카드를 옮기지 않는다. 컬럼은 티켓 파일의 state 필드를 따르고 그 파일은 에이전트만 쓰므로, 실행 중인 티켓은 에이전트가 파일을 고칠 때까지 Todo에 머문다. TUI는 실제 TTY가 필요하다. 스크립트에서 띄우면 조용히 종료된다.

  10. 또는 서비스로 돌리고 웹 보드 열기

    목표: 같은 오케스트레이터를 백그라운드에서 브라우저 UI와 함께. service start는 먼저 symphony doctor를 돌리고, 시작한 워크플로를 .symphony/run/<workflow-hash>.json에 기록한다. 그래서 같은 WORKFLOW.md를 실수로 다른 포트에서 두 번 띄울 수 없다.

    symphony service start ./WORKFLOW.md --port 9999
symphony service status ./WORKFLOW.md
symphony service logs ./WORKFLOW.md
# later: symphony service restart ./WORKFLOW.md  |  symphony service stop ./WORKFLOW.md

    확인: http://127.0.0.1:9999/를 연다. 실행 중 카드에는 Pause / Resume 버튼이 있고, 헤더의 refresh 버튼은 poll + reconcile을 실행하며, 헤더에는 agent.feature_base_branch(새 기능 브랜치의 시작점)와 agent.auto_merge_target_branch(Done 머지가 들어갈 곳)를 고르는 실제 로컬 git 브랜치 드롭다운이 있다. 보드는 루프백 전용이다.

    선택: Bearer 토큰. 실행 전에 export SYMPHONY_API_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"를 설정하면 모든 운영 /api/ 요청에 Authorization: Bearer가 필요해지고, 웹 앱은 첫 401 뒤에 토큰을 물어본다. 값은 WORKFLOW.md, 셸 히스토리, 로그에 남기지 않는다.

  11. 티켓이 상태를 지나가는 것을 따라가기

    목표: 기다리는 동안 각 컬럼의 뜻을 이해한다.

    상태에이전트가 하는 일
    Todo분류하고 In Progress로 보낸다. 본문과 Acceptance Criteria 섹션이 있는 티켓은 모델 턴 없이 넘어간다.
    In Progress계획 + TDD 구현 + 자기 검토. worktree 안의 symphony/<ID> 브랜치에서.
    Verify리뷰 + QA + 머지 게이트. 기능 브랜치를 대상 브랜치에 머지해야 Document로 갈 수 있다.
    Document문서 + 위키 반영. 개입이 필요 없으면 Done.
    Human ReviewDone 전에 사람이 개입하거나 명시적으로 검토한다. 에이전트는 여기서 멈추고 결정은 내가 한다.
    Done검증 완료.

    Human Review에서 보이는 것: 카드가 종료 상태 컬럼에 멈춰 있고 ● 표시가 없다. TUI에서 카드에 포커스하고 c를 누르면 Done으로 승인되고, 웹 보드에서도 Done으로 옮길 수 있다. Symphony가 대신 Done을 확정하는 일은 없다.

  12. 결과 확인하기

    목표: 코드, 메모, 실행 기록이 어디 있는지 찾는다.

    symphony board show TASK-1               # the agent's ## Resolution lives in the body
ls ~/symphony_workspaces/TASK-1          # workspace it operated in
symphony runs ./WORKFLOW.md --limit 5    # recent run-registry attempts
git branch --list 'symphony/*'           # the ticket's feature branch

    확인: 티켓 끝에 ## Resolution 섹션이 붙는다. 커밋되는 산출물은 티켓 브랜치의 docs/<TICKET-ID>/<stage>/ 아래에 있다. 리뷰어가 열어볼 파일(스크린샷, 리포트)은 호스트의 .symphony/artifacts/<TICKET-ID>/로 복사되어 티켓의 ## Artifacts 목록과 웹 티켓 서랍에 나타난다. headless 모드(tui 없이 symphony ./WORKFLOW.md)에서는 워크플로 옆에 WORKFLOW-PROGRESS.md가 매 틱 다시 쓰인다. 읽기 전용 출력이니 손으로 고치지 않는다.

  13. 일상 운영

    할 일방법
    워커 일시정지 / 재개포커스된 실행 중 카드에서 P, 또는 웹 버튼
    재시도자동. 실패한 워커는 ↻ 재시도 큐에 들어가 agent.max_retries까지 간격을 늘려가며 다시 시도한다. r은 새로고침 + 재폴링을 강제한다
    아카이브Done 카드에서 a. tracker.archive_after_days가 오래 방치된 종료 티켓도 정리한다
    Document 건너뛰기위키 반영이 필요 없는 티켓은 포커스 후 S
    티켓 수동 이동symphony board mv TASK-1 Blocked 또는 symphony board update TASK-1 --state Blocked --add-blocked-by BUG-7. 오케스트레이터는 다음 폴 틱에 다시 평가한다

    확인: 수동 이동은 막힌 것을 풀 때만 쓴다. 보통은 WORKFLOW.md의 단계별 프롬프트 파일에 따라 에이전트가 직접 티켓을 옮긴다.

  14. 여러 프로젝트

    목표: 컨트롤 플레인 하나로 보드 여러 개를 돌린다.

    symphony project list
symphony project start my-app
symphony project status
symphony project stop my-app
symphony hub                             # central UI for every registered project

    확인: Hub와 각 프로젝트 보드는 정식 저장소, 워크플로, "Issues are stored here" 경로를 보여준다. 다른 프로젝트를 고르면 필요할 때 그 서비스가 시작된다. 이전 프로젝트의 서비스와 워커는 원래 저장소에서 계속 돌기 때문에, 프로젝트를 바꿔도 진행 중인 작업이 다른 곳으로 옮겨가지 않는다.

  15. 문제 해결과 다음 읽을 것

    증상해결
    doctor가 FAIL 출력그 줄이 가리키는 것만 고치고 다시 돌린다. 가장 흔한 것은 자리표시자 클론 URL이다. worktree 기본값이나 : noop으로 바꾼다. 종료 코드 2는 YAML 자체를 읽지 못한 것이다.
    워커 종료, 카드에 ↻Symphony는 agent.max_retries까지 간격을 늘려 재시도한 뒤 에스컬레이션하고 티켓을 세워 둔다. 마지막 오류는 symphony runs ./WORKFLOW.md --limit 5와 symphony service logs ./WORKFLOW.md에서 읽는다.
    에이전트가 몇 분째 조용함stall_timeout_ms 안에 진행 이벤트가 없는 워커는 취소된다. 무거운 레인(lane, 컬럼)만 agent.stall_timeout_ms_by_state: {Verify: 900000}으로 넓힌다. 로그는 stderr로 나가므로 symphony tui ./WORKFLOW.md 2>> log/symphony.log로 남긴다.
    포트가 이미 사용 중doctor가 충돌을 보고한다. --port N으로 덮어쓰거나 symphony service status ./WORKFLOW.md를 본다. 같은 워크플로는 두 번 뜨지 않는다.
    TUI가 조용히 꺼짐실제 터미널(TTY)이 필요하다. 포그라운드 터미널에서 실행하거나, symphony ./WORKFLOW.md로 headless로 돌리고 WORKFLOW-PROGRESS.md를 따라간다.
